02 / PROBLEMS

问题与处理

两个项目实现中出现的 6 个具体问题，以及对应的处理方案。

P-01检查通过、扣减之前被别人抢走，怎么办？

把「检查 + 扣减 + 打标记 + 写流水」合并成一次 Redis 原子执行，中间不留任何可被插入的窗口；校验顺序按成本排：先全局、低成本的时间与状态，用户维度的 Set 查询放最后。

↳ shop-pick · 秒杀资格判定

P-02Redis 扣了、数据库没落，账不就错了？

承认这个窗口存在，用三层收敛：生产失败 / 消息超时 / 消费失败三处自动回滚（删 key 而非加减库存，保证幂等），定时任务双向对账并带宽限期避开在途消息，重试耗尽则落库告警交人工。

↳ shop-pick · 一致性闭环

P-03缓存穿透和击穿，为什么不能一套方案解决？

两者成因不同：穿透是查不存在的数据，用布隆过滤器拦截 + 空值缓存兜误判；击穿是热 key 失效瞬间大量并发回源，用分布式锁 + 双重检查做单飞。

↳ shop-pick · 多层缓存

P-04消息重复投递，订单会重复创建吗？

幂等键用消息 uuid 而不是 orderId —— 一次扣减可能被重投多条不同的消息，用订单号反而拦不住。再配 Redis 前置 Set 与数据库侧查重做双保险。

↳ shop-pick · 幂等设计

P-05工具返回的对象，怎么回到前端？

塞进文本流会把结构弄丢。做法是请求开始生成 requestId → 经 ToolContext 传给工具 → 工具把结果暂存 → 流尾按 requestId 取出、包装成结构化事件下发并清理。

↳ knowpath · Tool Calling

P-06单个外部工具挂了，整个问答就该一起挂吗？

不该。健康状态按服务维度隔离：连续失败到阈值就熔断进快失败窗口，窗口结束放行一次探测，成功即恢复。工具不可用时返回可读原因，模型读到后改用别的能力回答。

↳ knowpath · 工具治理思路

04 / PRACTICE

工程实践

构建、提交、配置、部署四个环节，以及一条外部依赖取舍。

T.01

构建与依赖

Maven 多模块聚合：统一版本管理、按需依赖、模块名与包名一致，避免「改一个模块要顺带改三处」。

T.02

提交与历史

提交信息写清「改了什么、为什么」，而不是 update。重建仓库前先把旧历史备份好再动手。

T.03

配置与密钥

敏感配置一律外部注入：不入库、不留明文。仓库里用占位值，真实值走配置中心或环境变量。

T.04

部署与排障

Dockerfile + 启动脚本做容器化；日志分层、关键链路埋点，先能定位再谈优化。

T.05

外部依赖

图形与动效全部自建，不引用第三方图片服务；访问者网络受限时不会出现加载失败导致的破图。
